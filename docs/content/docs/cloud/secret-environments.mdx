title: Manage secret environments

A secret environment is a named configuration and access scope inside one
project. Use it to keep development, staging, production and preview credentials
separate. This Cloud management surface is **Alpha**.

It is separate from the [managed sandbox environments](/cloud/releases-and-environments)
used to run synthetic contract tests. Creating either kind does not provision,
populate or authorize the other.

## Choose a scope

| Kind | Intended use | Access boundary |
| --- | --- | --- |
| Development | Local developer work | Developer grants are allowed only when unprotected. |
| Staging | Integration and pre-release checks | Developer grants are allowed only when unprotected. |
| Production | Live application credentials | Always protected; consumption requires a registered workload and grant. |
| Preview | Temporary application scope | Requires an expiry; developer consumption grants are unavailable. |

Protection restricts environment changes to owners and excludes developer
consumption grants. Binding, grant and activation administration already require
an owner in every environment. Project membership is separate from runtime
authorization. See the [operation-level role table](/cloud/secrets#project-roles).

Application consumption remains subject to the
[qualified runtime limits](/introduction/support-matrix#cloud-and-applications).
An environment named `production` does not establish production runtime support.

## Create an environment

Prerequisite: membership with permission to create the intended kind. Use a
disposable staging scope for your first test.

1. Open your project's **Secrets** page.
2. Open **Environment settings**, then select **Create environment**. If the
   project has none, use the initial **Create environment** action.
3. Enter a unique name such as `staging-payments` and select its kind.
4. Choose protection where appropriate. Production is always protected.
5. Review the destination and create the environment.

Names begin with a lowercase letter, use letters, digits, underscores or
hyphens, and contain at most 64 characters. The dashboard gives new previews a
24-hour expiry. The preview CLI accepts an explicit future expiry up to seven
days away.

The new scope has no inherited values or access grants. Project-wide secret
definitions remain visible in its inventory as missing a value. Add the intended
values, bindings and grants explicitly. There is no automatic copy or promotion
from staging to production.

## Select the destination before editing

The Secrets context header keeps the selected name, protection, state and
expiry visible. Every value or access change applies to that selected scope.
The page asks you to discard unsaved input before switching environments.

The local runtime's profile name is a separate choice. A profile named
`cloud-staging` maps explicitly to a Cloud project ID and environment ID in
`AxiomSecrets.toml`. Selecting an environment in the browser does not retarget a
running CLI process, and a matching name does not create a connection.

Use [`--environment` explicitly](/tooling/secrets-cli#select-local-and-cloud-profiles)
when starting a protected runtime. Local `.env` files are not uploaded or merged
into Cloud automatically.

## Disable, enable and expire

Open **Environment settings** to inspect the ID, kind, protection, state and
expiry. An enabled environment offers **Disable environment**. A disabled
environment offers **Enable environment**.

Disabling denies runtime consumption and invalidates the environment's leases.
It retains encrypted versions and audit history. Enabling permits resolution
only when version, binding and identity policies allow it. It does not undo
grant revocations or restore disabled versions. Environment updates invalidate
existing leases, so consumers must establish fresh authorized access.

Preview expiry closes runtime access without deleting history. The dashboard
does not extend expired previews; create a fresh scope there. Owners using the
preview CLI can submit a reviewed environment update with a future expiry
within the same seven-day limit and the current revision. Enabling alone does
not extend an expiry.

To verify isolation, select two environments and compare their value and access
metadata. Adding a candidate in one should leave the other without that value.
Do not use a real production credential for this check.

## Finish a temporary environment

Revoke temporary grants, disable temporary workload identities, and disable the
environment when finished. The module retains records for audit rather than
providing a general environment deletion flow. Revoke credentials at their
upstream providers separately.

For an unexpected denial, check state, expiry and protection first, then the
selected runtime profile and exact IDs. Continue with
[adding values and runtime access](/cloud/secrets) or the
[environment CLI commands](/tooling/secrets-cli#manage-cloud-environments).
