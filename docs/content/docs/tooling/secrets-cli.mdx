The `axiom secrets` namespace below is **Experimental**, verified with the
matching source-preview CLI 0.149.1 on macOS arm64. Published CLI 0.149.0 and
signed web host 0.6.12 do not carry the protected runtime qualification. This
page is a reference for an already provisioned matching preview, not a public
installation recipe. Use the [Cloud Dashboard guide](/cloud/secrets) for the
deployed **Alpha** management workflow.

Check the executable you intend to use:

```bash title="Terminal"
axiom --version
axiom secrets --help
```

If `secrets` is unknown, use the dashboard. Installing the current public CLI
does not by itself enable this preview. See the
[target support limits](/introduction/support-matrix#cloud-and-applications)
before attempting runtime consumption.

## Inputs and output

Run local commands from the application directory containing
`AxiomSecrets.toml`. An optional `ROOT` defaults to `.`. Cloud management commands
accept an explicit project slug and require `axiom login`. Browser sign-in and
native CLI device login are separate sessions.

| Input | Meaning |
| --- | --- |
| `--project PROJECT` | Project slug, such as `payments-api`. |
| Cloud `--environment ENVIRONMENT_ID` | Configuration environment UUID returned by `environments`. |
| Local `--environment PROFILE` | Exact profile name in `AxiomSecrets.toml`, such as `development`. |
| `SECRET_ID`, `VERSION_ID`, grant/workload IDs | UUIDs returned by management commands. |
| Numeric version in a binding or runtime profile | Immutable version number such as `1`, rather than the version UUID. |
| `--revision N` / `expected_revision` | Current metadata revision used to reject stale changes. |

Cloud commands print JSON metadata, never saved values. The identifiers below
are placeholders; replace them with your own metadata. There is no saved-value
read, reveal, export or automatic whole-dotenv import command.

## Manage Cloud environments

```bash title="Terminal (matching preview required)"
axiom login
axiom secrets environments --project payments-api
axiom secrets create-environment --project payments-api \
  --slug staging-payments --kind staging
axiom secrets create-environment --project payments-api \
  --slug production --kind production --protected
```

Creation returns an `id`; listing returns IDs, kind, protection, state, revision
and expiry. Kinds are `development`, `staging`, `production` and `preview`.
Production requires `--protected`. A preview requires
`--expires-at RFC3339_TIMESTAMP`, in the future and no more than seven days away.
New scopes inherit no values or grants. See
[environment rules and roles](/cloud/secret-environments).

Owners update an environment through a private metadata file. This example
disables an unprotected staging environment. Replace the revision with its
current value and preserve the actual protection and expiry settings:

```json title="environment-update.json (template)"
{
  "status": "disabled",
  "protected": false,
  "expected_revision": 1,
  "expires_at": null
}
```

```bash title="Terminal"
chmod 600 environment-update.json
axiom secrets update-environment --project payments-api \
  --environment ENVIRONMENT_ID --file environment-update.json
```

`status` is `active` or `disabled`. Production cannot become unprotected. Preview
updates require a valid future expiry within seven days. An update invalidates
existing leases; enabling does not restore revoked access.

## Define, save and activate

```bash title="Terminal (matching preview required)"
axiom secrets define payments/api-key --project payments-api \
  --purpose authenticateHttp --description "Payment provider authentication"
axiom secrets list --project payments-api
axiom secrets set SECRET_ID --project payments-api --environment ENVIRONMENT_ID
axiom secrets versions SECRET_ID --project payments-api --environment ENVIRONMENT_ID
```

`define` returns a secret ID. Supported purposes are `authenticateHttp`,
`signRequest`, `verifyToken`, `connectDatabase` and `authenticateWorker`.
`--description` defaults to an empty string. `list` returns project-wide
definitions, not selected-environment values.

`set` opens a masked prompt. It saves a candidate and returns metadata including
its ID. It does not activate or authorize consumption. For automation,
`--stdin` reads one raw credential of 1 to 65,536 bytes:

```bash title="Terminal (private input file containing one credential)"
axiom secrets set SECRET_ID --project payments-api \
  --environment ENVIRONMENT_ID --stdin < /private/path/payment-key
```

Keep that input owner-only and outside version control. Stdin preserves bytes,
including a trailing newline. Do not pass a whole `.env` document or place a
value in a command argument, shell history, build log or description.

`versions` returns up to 200 recent versions with UUID, numeric version, status,
creation time and destruction eligibility. It does not return the mutation
revision. As an owner, obtain the current environment-secret revision described
below, then review and activate the intended candidate:

```bash title="Terminal"
axiom secrets activate SECRET_ID VERSION_ID --project payments-api \
  --environment ENVIRONMENT_ID --revision CURRENT_REVISION
```

Refresh metadata after a successful mutation. On a revision conflict, re-read
and review before retrying. Activation leaves explicit runtime pins and running
generations unchanged. A connection failure can leave a write unconfirmed;
inspect metadata before resubmitting a value.

### Revision metadata

Version actions use the **environment-secret** revision, rather than the numeric
version or the environment's revision. The preview CLI has no environment-secret
inventory or binding-list command. The authenticated management API exposes the
missing reference metadata through these read-only routes:

| Route under `/api/v1/projects/PROJECT/configuration-environments/ENVIRONMENT_ID` | Revision source |
| --- | --- |
| `GET /secrets` | Find the secret by `id`; use its `revision` for version actions. |
| `GET /secret-bindings` | Find the binding by `id`; use its `revision` for binding updates. |

Use an authorized native management session for API requests. Do not copy a
browser cookie or put tokens in a URL. `axiom secrets environments` supplies the
separate environment revision for `update-environment`. The dashboard obtains
these revisions automatically if you prefer to manage changes there.

## Bind and grant

These commands require an owner. JSON files passed through `--file` must be
owner-only regular files, without symlinks or multiple hard links, and at most
32,768 bytes. They contain reference metadata, never a credential.

Inspect a compiled private backend plan:

```bash title="Terminal"
axiom secrets requirements backend.server.json
```

The result includes `planSha256`, declared requirements and resource consumers.
It is not a complete discovery catalog for authentication or sandbox consumers.
Use the exact compiled plan and reviewed consumer declaration.

This binding template uses HTTP authentication. Replace every placeholder and
review the origin, method and path restriction:

```json title="binding.json (template)"
{
  "secret_id": "SECRET_UUID",
  "requirement": "payment",
  "consumer": "resource:payments",
  "purpose": "authenticateHttp",
  "plan_sha256": "EXACT_64_CHARACTER_LOWERCASE_SHA256",
  "package_sha256": null,
  "version": 1,
  "destination_policy": {
    "origin": "https://api.payment-provider.example",
    "method": "POST",
    "path_prefix": "/payments"
  },
  "expected_revision": 0
}
```

Use `expected_revision: 0` for creation and the current binding revision for an
update. `version: null` follows the active version during eligible new
resolution. Sandbox consumers additionally require the exact canonical package
fingerprint. Their deployment injection remains a separate explicit requirement.

```bash title="Terminal"
chmod 600 binding.json
axiom secrets bind --project payments-api \
  --environment ENVIRONMENT_ID --file binding.json
```

A separate grant authorizes one project member in an unprotected development or
staging environment. Set a future RFC 3339 expiry no more than 90 days away:

```json title="grant.json (template)"
{
  "binding_id": "BINDING_UUID",
  "user_id": "PROJECT_MEMBER_UUID",
  "workload_id": null,
  "expires_at": "FUTURE_RFC3339_TIMESTAMP"
}
```

```bash title="Terminal"
chmod 600 grant.json
axiom secrets grant --project payments-api \
  --environment ENVIRONMENT_ID --file grant.json
axiom secrets grants --project payments-api --environment ENVIRONMENT_ID
```

For a workload, set `workload_id` and `user_id: null`. Register the exact workload
first with `register-workload --file workload.json`. Its JSON fields are
`issuer` (`https://accounts.google.com`), `subject` (the Google identity token
subject), `audience` (the configured secret runtime audience), `plan_sha256`, and
optional `deployment_id`. The Cloud runtime audience is
`https://api.axiomcore.dev/runtime/v1/secret-leases`. Registration does not grant
access or qualify an unsupported runtime target.

## Select local and Cloud profiles

`axiom secrets init .` creates a reference-only `AxiomSecrets.toml` scaffold and
refuses to overwrite an existing file. Edit it to select each source explicitly.
This complete minimal file defines one local requirement:

```toml title="AxiomSecrets.toml"
format = "axiom-secret-bindings/v1"

[environments.development.secrets.payment]
source = "dotenv"
file = ".env.development"
key = "PAYMENT_KEY"
```

Supply `PAYMENT_KEY` in your private `.env.development`, set its mode to `0600`,
and exclude it from version control and public assets. The file must belong to
the runtime user, stay within the selected root and have one hard link. Do not
source it into a shell. There is no parent discovery, interpolation, shell
execution or automatic fallback to another source.

```bash title="Terminal (application directory)"
chmod 600 .env.development
axiom secrets inspect . --environment development
axiom secrets check . --environment development
axiom secrets check . --environment development --resolve
```

`inspect` shows references. `check` validates configuration; `--resolve` also
checks local sources without printing values. For this file, successful resolved
output is:

```json title="Expected output"
{"bindings":["payment"],"resolved":true,"valid":true}
```

A Cloud profile also supplies exact project, environment and binding IDs. Add
this partial section to the same file, replacing the placeholders:

```toml title="AxiomSecrets.toml (additional Cloud profile)"
[environments.cloud-staging.secrets.payment]
source = "axiom-cloud"
secret = "payments/api-key"
version = "1"

[environments.cloud-staging.cloud]
identity = "development"
project_id = "PROJECT_UUID"
project_slug = "payments-api"
environment_id = "ENVIRONMENT_UUID"

[environments.cloud-staging.cloud.bindings]
payment = "BINDING_UUID"
```

`version` is an immutable numeric version expressed as a string. Development
identity requires an eligible environment and a separate member grant. A Cloud
profile cannot use `check --resolve`: validate its authorization against the
exact executable plan when starting the supported runtime.

For an existing compiled application with a reviewed deployment configuration,
start one profile explicitly:

```bash title="Terminal (matching macOS arm64 preview required)"
axiom serve service.acore --deployment deployment.json \
  --environment development --watch --port 8080
```

Use `--environment cloud-staging` to select the Cloud profile instead. This is a
runtime invocation template, not a complete application: its Acore declaration,
consumer, private plan, deployment and Cloud binding must agree. Compilation
does not ingest value files. Watch prepares a replacement generation before
switching new requests; a failed replacement retains the old generation subject
to expiry and revocation. See [Acore and extension boundaries](/backend/runtime-secrets).

## Other commands and failure cases

All Cloud rows below take `--project PROJECT --environment ENVIRONMENT_ID`.

| Command suffix | Result |
| --- | --- |
| `workloads` | List workload registration metadata. |
| `register-workload --file FILE` | Register the exact identity and plan. |
| `disable-workload WORKLOAD_ID` | Disable registration and invalidate its leases. |
| `revoke-grant GRANT_ID` | Revoke that grant and affected leases. |
| `revoke SECRET_ID VERSION_ID --revision N` | Disable a version. This is different from revoking a grant. |
| `rewrap SECRET_ID VERSION_ID --revision N` | Re-encrypt stored material under the configured key; does not change the credential. |
| `destroy SECRET_ID VERSION_ID --revision N` | Permanently destroy an eligible disabled version after retention. |
| `audit [--before CURSOR]` | List up to 100 events; use the oldest numeric event ID as the next cursor. |

Invalid or missing profiles, unsafe file ownership/mode/linking, unavailable
identity, mismatched fingerprints, expired grants, disabled scopes and stale
revisions fail closed. An unsupported protected target is rejected. An audit or
Cloud outage can deny material use even before a lease expires. Use metadata
and [Activity](/cloud/secrets#investigate-or-stop-access) to investigate; do not
add credential dumps to troubleshoot.

After testing, revoke temporary grants and disable temporary workloads and
environments. Remove local credential files through your normal private-file
cleanup process. Continue with [secret lifecycle and rotation](/cloud/secrets)
or the [runtime security model](/backend/runtime-secrets).
