title: Testing contracts

The native test runner executes `TestConfig` suites against each suite's
configured base URL. It is a live HTTP/WebSocket test path, not a static source
assertion.

## Minimal suite

```acore
// list_tasks is an authored or extracted endpoint in the same contract.
testConfig(
  defaults: TestDefaults(timeoutMs: 5000),
  suites: [TestSuite(
    name: "Task API",
    baseUrl: "http://localhost:8080",
    tags: ["smoke"],
    checks: [CheckDef(
      label: "List tasks",
      route: Routes.list_tasks,
      expect: [
        StatusExpectation(value: 200),
        DurationExpectation(op: "lt", valueMs: 500),
        HeaderExpectation(key: "content-type", op: "contains", value: "application/json")
      ]
    )]
  )]
)
```

```bash
axiom test axiom.acore
axiom test axiom.acore --tag smoke
```

## Requests and expectations

`CheckDef` selects either a declared `route` or an explicit `url` and can
provide path/query parameters, body, and headers. It also controls retry,
timeout, skipping, captures, and continuation behavior.

Implemented expectation families cover:

- status and duration;
- response schema;
- body path comparisons and every/some/none quantifiers;
- headers; and
- named groups of expectations.

## Capture values

```acore
// A capture argument inside CheckDef(...).
CheckDef(
  url: "/login",
  capture: [ResponseCapture(path: "token", bindAs: "sessionToken", type: "string")]
)
```

Captured values are scoped test data for later checks/hooks. Do not print or
commit real production tokens.

## Lifecycle and isolation

Suites can declare typed lifecycle hooks. Use them to create/reset fixtures and
make state ownership explicit. Prefer a dedicated test or local mock base URL;
an explicit URL can perform real writes.

Run contract tests alongside, not instead of, the backend's unit/integration
tests and the consuming application's tests.

## Repeat retries and cancellation with logical time

Use the matching source build's [typed development scenarios](/tooling/axiom-test-runner#typed-development-scenarios)
for deterministic compiled managed-query behavior. Keep the complete Acore
resource/policy declarations, selected artifact identities and synthetic replies
in the same reviewed fixture project. `axiom scenario check` rejects wrong input
rules, undeclared failures and stale plans before acquiring resources.

A scenario uses an arrival barrier before advancing backoff, joins every started
operation, and checks terminal outcomes, physical calls and cleanup. A failed
assertion still drains work. Reports separate the primary failure from cleanup
failure and identify the actual execution level; a compiler-host scenario does
not certify persistence, transport or native OS behavior.
