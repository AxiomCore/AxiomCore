Axiom Cloud is the hosted control plane for your contracts and their
operational evidence. It has two surfaces: the
[Cloud Dashboard](https://app.axiomcore.dev) in the browser, and the API that
the Axiom CLI calls for `axiom login`, `axiom project`, `axiom release`,
`axiom pull` and `axiom deploy`.

Cloud is optional. You do not need it to write Acore, run local checks or build
an unsigned development artifact.

## How Cloud is organized

```mermaid title="How Axiom Cloud organizes workspaces, projects and their records"
flowchart TD
  W[Workspace] --> M[Members and invitations]
  W --> P[Project]
  P --> R[Contract releases]
  R --> L[latest channel]
  R --> PR[Contract pull requests]
  P --> S[Managed sandbox and tests]
  P --> E[Project environments]
  E --> SE[Secrets]
  E --> DB[Managed database]
  P --> O[Observability]
```

A **workspace** groups members and projects. A **project** owns everything
else: immutable contract releases, the `latest` channel that consumers pull
from, contract pull requests, a managed sandbox for tests, and observability
data. A project **environment** (such as `development`, `staging` or
`production`) is a separate configuration scope. Secrets and a managed database
attach to one environment.

## What Cloud does today

| Capability | Status | Scope |
| --- | --- | --- |
| Accounts, workspaces and projects | **Alpha** | Browser sessions, CLI device login, memberships, invitations, project roles, settings and signing keys. |
| Contracts and releases | **Alpha** | Immutable versions, manifests, verification, semantic diff, durable pipeline evidence, an explicit `latest` channel, activation and rollback. |
| Contract pull requests | **Alpha** | Proposals, semantic changes, review comments and review states. |
| Managed sandbox and mock | **Alpha** | A project-scoped synthetic environment, where the deployment enables managed environments. |
| Contract tests and release policy | **Alpha** | Declared tests against the matching sandbox, with saved results and release-policy outcomes. |
| Runtime observability | **Alpha** | Scoped OTLP sources, traces, traffic, logs, retention, alerts and security posture. |
| Project secrets | **Alpha** management; **Experimental** protected consumption | Write-only values, versions, bindings, grants and activity. Application use has separate [runtime limits](/backend/runtime-secrets). |
| Managed databases | **Alpha** | Database preferences, provisioning in available locations, suspend, resume, access rotation and deletion. |
| Hosted database connections, hosted migrations and managed application authentication | **Coming soon** | Storage can be provisioned, but applications cannot connect to it through Cloud yet. |
| Database archive, restore and customer-owned connections | **Coming soon** | No hosted recovery SLA is announced. |
| Public paid checkout | **Coming soon** | Pro can be selected as a preference. Only controlled test checkout runs today. |
| Hosted CI/CD for every repository | **Coming soon** | Release pipelines process Axiom artifacts. They do not replace general repository CI. |
| Axiom Studio, Acode and Axiom Marketplace | **Coming soon** | Planned products. They are not hidden parts of the Cloud Dashboard. |

## Choose local or connected work

Use local commands for authoring, evaluation, security and domain validation,
semantic diff, mocks and contract tests. Use Cloud when a team needs shared
identity, immutable distribution, signing provenance, review records, release
channels, managed environments or retained runtime evidence.

Cloud records do not replace backend authorization or code review. A signed
contract states where an artifact came from. A passing contract test states
that the declared checks passed against the selected environment.

## Start

Cloud access is invite-only during the Alpha. The first Cloud command asks for
a referral code. Without one, join the waitlist with `axiom join <EMAIL>`.

```bash title="Terminal"
axiom login
axiom project list
axiom project link
axiom build --release --version 1.2.0 --out backend.axiom
```

The CLI resolves the linked project from the current directory. In automation,
pass an explicit `--project` and immutable `--version`, and keep the released
project and version with your deployment evidence.
