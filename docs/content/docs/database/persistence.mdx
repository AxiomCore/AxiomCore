Define storage mappings in backend Acore. CLI 0.149.0 compiles the private plan and, during development startup, migrates the linked database before accepting requests. PostgreSQL and SQLite share a closed typed operation interface; frontend contracts contain the public API surface.

## A minimal resource mapping

```acore title="Acore excerpt"
resource tasks(lifetime: ProviderLifetime.application) {
  operation list(input: Models.Empty, output: List<Models.Task>, effect: EffectKind.read)
  operation create(input: Models.NewTask, output: Models.Task, effect: EffectKind.write)
}

storage tasks(schema: "../database/schema.acore", resource: Resources.tasks) {
  select list(table: "app.tasks", fields: {id: "id", title: "title"}, limit: 100)
  insert create(table: "app.tasks", values: {id: Input.title, title: Input.title},
    fields: {id: "id", title: "title"})
}
```

For SQLite use its schema path and `main.tasks`. Mapped field types, resource signatures, effect bounds, primary keys and tenant columns are checked against the actual compiled schema. PostgreSQL application tables use forced RLS and an unelevated application login role; the development example declares the managed role with an opaque `credentialRef` slot. Axiom generates and stores the role credential privately, separately from the operator connection.

```sh title="Terminal"
axiom run backend/main.acore --database-url "$DATABASE_URL" --port 8093
# SQLite variant:
axiom run backend/sqlite.acore --port 8093
# Second terminal:
axiom run frontend/main.acore --port 5173
```

The backend emits a development API key for the local UI. Private bindings and the key registry are generated under `.axiom/` with owner-only permissions. A production deployment supplies its reviewed authentication, signer and provider policy. No developer-maintained runtime-spec or deployment JSON is needed for the ordinary example.

## Program rules

Select/insert/update/delete declarations use logical tables and explicit API-field mappings. Values use `Input.field`, trusted `Claims.field` or literals. SQL text and arbitrary query constructors are not accepted. Inputs are native bound parameters; tenant selection comes from authenticated identity and is added to every generated predicate/write. Limits, deadlines, response bounds, result validation and transaction rollback are enforced by the host.

`constraint`, `failure: Failures.name` and `message` map a declared constraint failure to a typed public failure. Supported serialization conflicts retry the complete aborted transaction within the declared attempt bound. Ambiguous commit outcomes are reported rather than retried blindly. Readiness checks reject drift or an unapplied schema.

The ordinary development profile provides bounded typed select/insert/update/delete programs. Advanced application receipts, batch/savepoint strategies and special codecs keep the retained certified transaction profile and receive capability diagnostics in the ordinary adapter.

## Retained certified programs without authored JSON

The advanced `examples/database-persistence` fixture now expresses its private programs in `backend/storage.acore`. A transaction block names explicit query steps, its result, isolation, retry bound, idempotency receipt and constraint failures:

```acore title="Acore excerpt"
storage tasks(schema: "../database/schema.acore", resource: Resources.tasks) {
  transaction read(readOnly: true, isolation: "serializable", maxAttempts: 3, result: "task") {
    select task(table: "app.tasks", fields: {id: "id", title: "title"},
      equals: {id: Input.id}, limit: 1, many: false)
  }
}
```

This advanced transaction profile requires separately qualified deployment
configuration. Start with the [minimal app](/examples/task-app) for ordinary
select, insert, update, and delete operations; a successful local run does not
qualify advanced transaction guarantees.

## Endpoint wiring and browser provider

Endpoints explicitly select a managed action with `handle(action: ...)`. That action calls a resource operation. The source-owned `storage` declaration implements the operation with a typed query:

```acore title="Acore excerpt"
storage tasks(schema: "../database/schema.acore", resource: Resources.tasks) {
  delete delete(table: "app.tasks", equals: {id: Input.id},
    fields: {id: "id", title: "title"})
  binding rows(table: "app.tasks", model: Models.Task, store: "tasks",
    fields: {id: "id", title: "title"})
}
```

The operation must also be declared on `Resources.tasks` with `EffectKind.delete`. Its action awaits `Resources.tasks.delete(input: {id: Input.id})` and returns the deleted record. The endpoint declares its response, failures and list-cache invalidation. The native provider binds the ID and adds the authenticated tenant predicate; naming an endpoint `delete_task` does not create deletion logic.

The database playground examples use the same checked managed-flow interpreter with a bounded in-memory provider for these typed storage operations. Bindings supply field/table associations; endpoint mock mutations do not implement CRUD. The list endpoint's initial mock state is browser fixture data only. Browser authentication and tenant context are synthetic and confer no native authority. Unsupported host operations require the local CLI.

Downloaded examples contain executable native handlers, hidden artifact references, web targets and instructions for the real API key. PostgreSQL examples declare application grants/RLS and document seeding any referenced parent rows through the Axiom SQL console. Run preserves compatible preview data, invalid changes preserve the accepted state, and data/history resets are explicit. Native and browser evidence remain distinct.

See [Database contracts](/database/contracts) and [SQLite contracts](/database/sqlite) for run, migrate, status, history, comparison and rollback.
