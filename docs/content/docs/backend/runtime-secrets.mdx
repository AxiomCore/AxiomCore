Use a project's **Secrets** page to keep separate values and access grants for
development, staging, production, and expiring previews. Cloud management is
**Alpha**. Protected application consumption is **Experimental** in the matching
source preview on macOS arm64, including server WASM extensions. The published
CLI 0.149.0 and signed web host 0.6.12 do not establish support for this preview.
See [support and availability](/introduction/support-matrix).

For step-by-step tasks, use [Manage project secrets](/cloud/secrets),
[Manage secret environments](/cloud/secret-environments), and the
[preview CLI reference](/tooling/secrets-cli).

## Add a Cloud secret

Open your project in the [Cloud Dashboard](https://app.axiomcore.dev), then choose
**Secrets**. Create a logical environment and a secret definition with its
intended purpose. Select both before entering a value. Saving clears the input
and creates a candidate version. Saved values have no reveal or download action.

An owner activates the candidate using the current configuration revision. A
binding maps a declared requirement to an environment secret and reviewed
consumer. A separate expiring grant authorizes a developer or workload to use
that binding. Creating a definition, writing a value, or owning a project does
not grant consumption.

Production environments are protected. Developer consumption grants apply only
to unprotected development and staging environments. A production workload uses
its separately registered identity. New environments contain no inherited
values or grants. Preview expiration closes access while retaining versions and
audit history.

## Choose the runtime source explicitly

The protected preview uses a reference-only `AxiomSecrets.toml`. It selects one
source for each logical requirement. There is no automatic parent-directory
dotenv discovery, source precedence, interpolation, shell execution, or fallback
from Cloud to local values.

This partial binding example names a local source without including its value:

```toml title="AxiomSecrets.toml (partial example)"
format = "axiom-secret-bindings/v1"

[environments.development.secrets.paymentsCredential]
source = "dotenv"
file = ".env.local"
key = "PAYMENTS_API_KEY"
```

The private file must belong to the runtime user and be readable only by that
user. Relative paths stay inside the selected project root. Symlinks and files
with multiple hard links are rejected. Compilation does not read the value file. Keep it outside version
control and public assets. Cloud bindings additionally require the exact
project, logical environment, binding identity, and immutable numeric version.
Changing a source does not require putting a credential into application code.

Declare the logical requirement and its consumer in backend Acore. This partial
snippet declares HTTP authentication; it does not contain or load a value:

```acore title="service.acore (partial backend declaration)"
secret payment(purpose: SecretPurpose.authenticateHttp)

resource payments(lifetime: ProviderLifetime.application, secrets: [Secrets.payment]) {
  operation call(input: Void, output: String, effect: EffectKind.read)
}
```

The reviewed deployment's adapter refers to `secret:payment`. Keep the provider
origin and other non-secret settings as separate `config:` references. Bind the
exact compiled consumer and plan to its allowed destination; a declaration by
itself is not an access grant. Inspect declared resource requirements with
[`axiom secrets requirements`](/tooling/secrets-cli#bind-and-grant).

Existing integrations that read process environment variables keep their
[documented provider workflow](/backend/integrations). They do not acquire the
protected preview's guarantees merely by using a `.env` filename. External
Python and Go application processes need an explicitly qualified integration.

## Keep consumption inside the owning boundary

| Consumer | What it receives | What performs credential use |
| --- | --- | --- |
| Backend action | A purpose-bound runtime capability | An approved native adapter |
| Server WASM extension | An opaque, invocation-scoped handle | The host broker and approved adapter |
| Frontend contract or extension | An authorized business-operation result | The application backend |
| Browser configuration | Selected public, typed fields | A separate public configuration projection |

Purposes include HTTP authentication, request signing, token verification,
database authentication, and internal worker authentication. A handle cannot be
converted to a string, logged as material, or returned in an ordinary business
model. An HTTP grant also restricts its consumer, origin, method, and path.
Redirects and ambient proxies cannot change that approved destination.

An extension needs explicit injection for its reviewed package, module,
authority, export, and purpose. A package declaration alone grants no access.
Rust, TypeScript, and Python server guests use the same opaque-handle boundary.
Frontend extensions cannot acquire shared project secrets.

The runtime profile must explicitly inject a server sandbox's logical handle.
This partial profile shows the required pins and destination restriction. Replace
the fingerprints with reviewed metadata; placeholders are not runnable:

```toml title="AxiomSecrets.toml (partial server sandbox injection)"
[environments.development.sandboxes.paymentsGuest]
plan_sha256 = "EXACT_BACKEND_PLAN_SHA256"
module_sha256 = "EXACT_WASM_MODULE_SHA256"
authority_sha256 = "EXACT_REVIEWED_AUTHORITY_SHA256"
export = "call"

[environments.development.sandboxes.paymentsGuest.secrets.payment]
binding = "payment"
origin = "https://api.payment-provider.example"
method = "POST"
path_prefix = "/payments"
```

The `payment` binding refers to the selected profile's secret source. The
extension's reviewed package permissions must also permit the secret purpose
and network operation. A Cloud sandbox binding additionally pins the canonical
package fingerprint. Missing or mismatched injection is denied before use.
With matching TypeScript SDK 0.1.3, a server guest requests the opaque handle
with `context.secret("payment")` and passes it to
`context.authenticated_request(...)`. These are server SDK calls, not a browser
secret retrieval API. The native broker performs the credential operation.

A frontend calls a named backend operation such as creating a checkout session.
The backend still enforces authentication, user and tenant authorization, CSRF
where applicable, quotas, and typed input and output. Do not expose a generic
URL relay or signing operation. Server-rendered pages keep credential use on the
server and send only public configuration and approved results in hydration.

The source web frontend path has mounted qualification. iOS and Android compile
checks do not establish mounted runtime support. Containers, Workers, other
native operating systems, and older readers fail closed for unsupported
protected capabilities; they have separate qualification gates.

## Rotate and revoke

Save a new candidate, activate it, and update the reviewed version pin. Activation
does not silently rewrite a running generation or an explicit pin. Protected
local watch prepares a replacement before switching new requests. Failed
preparation retains the previous generation, subject to its existing expiry and
revocation rules.

Disable a compromised version or revoke its grant to stop further authorized
use. Cloud leases last at most five minutes. Each material use requires central
audit acknowledgement, so a Cloud or audit outage can deny use before expiry.
Retire the credential at its upstream provider separately. Revoking an Axiom
handle does not revoke that upstream credential.

Audit history records identities, versions, consumers, operations, and outcomes
without values. A permitted event authorizes material use; it does not prove
that an upstream business transaction completed. Audit capacity exhaustion denies
new use and retains evidence.

The boundary includes the trusted runtime, adapters, operating system, encryption
service, and approved credential destination. It does not protect against a
compromised privileged host or every possible transformation by a malicious
upstream. Managed-source isolation also cannot identify arbitrary credentials
pasted directly into source code.

Use [local development](/backend/local-development) for the installed workflow,
and check [exact capability boundaries](/reference/capability-boundaries) before
selecting a preview runtime or deployment target.
