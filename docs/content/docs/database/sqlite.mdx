SQLite uses the same versioned developer commands as PostgreSQL. The CLI resolves the native SQLite library automatically and creates the file on migrate/run. No `sqlite3`, library flag or authored binding JSON is required. The selected Unix adapter requires SQLite 3.37+; macOS arm64 and Linux arm64 acceptance are recorded separately from production certification.

## Author and run

```toml title="AxiomDeps.toml"
# database/AxiomDeps.toml
type = "database"
targets = ["server"]
```

```acore title="Acore excerpt"
project(id: "example.tasks.sqlite", version: "1.0.0")
module example.tasks.sqlite

database tasks(engine: DatabaseEngine.sqlite) {
  manage(schemas: [Schemas.main], mode: ManagementMode.ownedObjects)
  schema main {
    table tasks(strict: true) {
      id: Sqlite.Text()
      title: Sqlite.Text()
      primaryKey(columns: [.id])
    }
  }
}
```

```sh title="Terminal"
axiom check database/schema.acore
axiom run database/schema.acore --database-file ./tasks.sqlite
axiom database migrate database/schema.acore --database-file ./tasks.sqlite
axiom database status database/schema.acore --database-file ./tasks.sqlite
axiom database history database/schema.acore --database-file ./tasks.sqlite
axiom database rollback database/schema.acore --database-file ./tasks.sqlite --steps 1
```

A SQLite URL such as `sqlite:./tasks.sqlite` or `sqlite:///absolute/tasks.sqlite` is also accepted. Omit the file/URL to use the owning project's persistent `.axiom/database/data/database.sqlite`. A PostgreSQL URL or PostgreSQL endpoint fields are an engine mismatch. This persistent migration profile rejects `:memory:`; disposable validator copies are managed internally.

The native console supports `\dt`, `\d tasks`, SQL, multiline statements, cancellation and EOF. Its connection message includes the file path for DBeaver or another SQLite inspector. Use the same file on subsequent commands and backend startup.

## Types and boundaries

`Sqlite.Text`, `Integer`, `Int`, `Real`, `Blob`, `Any` and explicit `Native(declared: ...)` describe SQLite storage and affinity. Strict tables use SQLite's strict-compatible declared types. Keys, foreign keys, checks, defaults, generated columns, indexes and supported views/triggers use the dedicated SQLite catalog. The managed scope is the entire `main` schema; attached databases remain gated.

Safe rebuilds preserve retained values and validate a consistent populated backup before target application. Foreign-key checks and native integrity checks run before acceptance. Unsupported type/rowid/sequence conversion strategies fail explicitly; Axiom does not silently coerce an existing identity. The internal ledger and schema commit atomically under a writer lock. Native locking, hot-journal/WAL recovery and the original qualified SQLite lifecycle remain separate from compiler-only evidence.

The version/prompt/CI/rollback rules are described in [Database contracts](/database/contracts). New versions bind schema and typed data intent, while compensation preserves history. Scoped risk authorization is required for removals and populated changes. Dropped data cannot be recovered by reconstructing a column.

## Backend persistence and playground

[Typed storage declarations](/database/persistence) connect native SQLite to the same backend resource interface used by PostgreSQL. Tenant predicates and inputs are generated from the closed program and bound through the native adapter. SQLite INTEGER values use lossless string codecs; TEXT is a natural fit for the minimal shared task example.

The main playground compiles real SQLite/database version metadata in WebAssembly and validates simulated rows against the schema. Preview migrations, version conflicts, comparison and rollback are simulation events. They never create files or authorize native database changes. Clean Source downloads contain Acore mappings and manifests.
