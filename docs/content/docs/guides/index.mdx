Adopt one boundary first. Keep the code and operational responsibilities your
application already owns, and prove one request through a supported client.

| Your starting point | AxiomCore adds | First guide |
| --- | --- | --- |
| FastAPI service | Extracted contract, review, tests, supported client | [FastAPI to web](/guides/fastapi-to-web) |
| Go service | Router/type extraction and a reviewed contract | [Go to web](/guides/go-to-web) |
| Existing browser or mobile frontend | Generated client and runtime boundary | [Frontend integrations](/frontend) |
| Existing PostgreSQL or SQLite database | Explicit inspection/adoption and schema history | [Existing database](/guides/existing-database) |
| Mixed Acore and existing code | A versioned artifact shared by the parts | [Incremental adoption](/guides/incremental-adoption) |

## Own the integration explicitly

| Concern | Application responsibility |
| --- | --- |
| Source of truth | Decide whether the API originates in existing code or authored Acore |
| Authentication | Issue and rotate credentials; configure authorization and error UI |
| Data | Choose ownership, migrations, backup, and recovery |
| Client lifecycle | Configure startup, base URLs, CORS/cookies, cache privacy, and disposal |
| Delivery | Deploy the executable service and its compatible consumers |

Acore is optional at supported integration edges. Framework support is bounded
by the [support matrix](/introduction/support-matrix), not by the portability of
the contract alone.

After one working request, add a [CI contract check](/testing/ci), review
[production readiness](/delivery/production-readiness), and document your
application's failure and recovery paths. For agent-assisted work, use the
[AI agent workflow](/guides/using-ai-agents).
