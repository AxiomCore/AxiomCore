`acore-semantic` speaks one protocol, `axiom-agent-semantic/v1`, over three
transports: MCP (`acore-semantic mcp`), JSON lines (`acore-semantic serve`) and
a one-shot command (`acore-semantic --root <project> < request.json`). The
operations, fields and errors are the same on all three.

<StatusNote status="experimental" title="Preview">
  The manifest marks `axiom-agent-semantic/v1` as `frozen` and lists the
  frozen operations in `protocol.frozen_operations`: the 11 read operations
  (see [Compatibility](#compatibility)). Which operations are fully
  implemented is in the [Support matrix](/semantic-service/support-matrix).
</StatusNote>

The protocol is defined by JSON Schema (draft 2020-12) files, published on
this site (see [Schema files](#schema-files)). The tables marked as generated
on this page are produced from those schemas and from the service's capability
manifest.

## Schema files

Each schema is a static file under
`https://docs.axiomcore.dev/semantic-service/schemas/`.
[`index.json`](https://docs.axiomcore.dev/semantic-service/schemas/index.json) lists every file with its URL, `$id` and title.

| File | Defines |
| --- | --- |
| [`envelope.request.json`](https://docs.axiomcore.dev/semantic-service/schemas/envelope.request.json) | Every request: the envelope fields each operation takes |
| [`envelope.response.json`](https://docs.axiomcore.dev/semantic-service/schemas/envelope.response.json) | Every response, success or error |
| [`error.json`](https://docs.axiomcore.dev/semantic-service/schemas/error.json) | The error object and its code vocabulary |
| [`common.json`](https://docs.axiomcore.dev/semantic-service/schemas/common.json) | Ids, workspace and snapshot identity, node references, limits, truncation, coverage, diagnostics |
| [`edits.json`](https://docs.axiomcore.dev/semantic-service/schemas/edits.json) | Edit operations, edit options, id maps, relocations, candidates, checks |
| `operations/<operation>.request.json` | The `params` of one operation (linked from each operation below) |
| `operations/<operation>.result.json` | The `result` of one operation; `x-errors` lists its error codes |

Each file's `$id` has the form
`https://schemas.axiomcore.dev/agent-semantic/v1/<file>`. The `$id` is the
schema's identifier, not a download location: nothing is served at
`schemas.axiomcore.dev`. The files on this site are the authoritative,
published copies. References between files are relative (for example
`../common.json#/$defs/path` from `operations/`), and a validator resolves
them against the `$id`, not against the URL a file was downloaded from. A
validator that fetches references on demand therefore tries
`schemas.axiomcore.dev` and fails. To validate, either load all 39 schema
files into your validator first, so it finds each one by its `$id`, or
configure it to map `https://schemas.axiomcore.dev/agent-semantic/v1/` to
`https://docs.axiomcore.dev/semantic-service/schemas/`.

## Conventions

- Field names and enum values are `snake_case`. Readers ignore fields they do
  not know; the service rejects unknown fields inside edit operations and
  apply preconditions, because ignoring a precondition could apply an edit you
  did not intend.
- Paths are relative to the project root with `/` separators, except
  `workspace.open` roots, which are absolute.
- SHA-256 values are lowercase hex. Timestamps are RFC 3339 with an offset.
  Diagnostic `line` and `column` start at 1; lengths and columns count Unicode
  scalar values.
- Over MCP each operation is a tool named with `_` for `.` (`node_find`). The
  tool's arguments are the request envelope without `protocol` and
  `operation`; the server fills `workspace`. The tool result's structured
  content is the response envelope.

The examples on this page run in order against a project directory named
`task-app` whose page is like the [quick start](/semantic-service/quickstart)
example, with a query and a mutation of a backend contract `tasks` and a list
of tasks. It also has the contract and the UI lock the Axiom CLI produces, so
it shows the contract fields. Ids, versions and digests from your own project
differ.

```acore title="task-app/main.acore, used by the examples on this page"
module tasks.app.ui

use contract Tasks from "tasks" audience "mobile"

app TasksApp { route "/" => Home }

page Home {
  state draft: String = ""
  query tasks = Tasks.list_tasks()
  mutation create = Tasks.create_task(title: draft)

  action submit() {
    create.run()
    draft = ""
  }

  view {
    View {
      Input(value: draft, placeholder: "Add a task")
      Button(label: "Add", on_press: submit)

      if tasks.pending { Text("Loading...") }
      else if tasks.error { Text("Could not load tasks") }
      else { List(items: tasks.data, key: |task| task.id, list_type: "single", span_count: 1, scroll_orientation: "vertical") { task => Text(task.title) } }
    }
  }
}
```

Values in angle brackets, such as `<workspace>`, stand for ids from earlier
responses. In responses, `…` marks text left out, including the end of long hashes.

## Request envelope

```json title="A request"
{
  "protocol": "axiom-agent-semantic/v1",
  "operation": "node.find",
  "workspace": "<workspace>",
  "snapshot": "latest",
  "limits": {"max_bytes": 65536},
  "params": {"query": "Add", "limit": 10}
}
```

{/* BEGIN GENERATED envelope-fields */}

| Field | Required | Type | Meaning |
| --- | --- | --- | --- |
| `protocol` | yes | `"axiom-agent-semantic/v1"` | Always this value. |
| `operation` | yes | `capabilities`, `workspace.open`, `project.overview`, `node.find`, `node.get`, `node.edits`, `graph.query`, `context.build`, `impact.analyze`, `changes.since`, `node.relocate`, `change.propose`, `change.inspect`, `check.run`, `change.apply`, `change.discard`, `edit.plan` | Every operation of v1. The capability manifest says which are implemented. |
| `workspace` | no | string (at most 256 characters) | Opaque workspace handle returned by `workspace.open`. Scoped to the host process and caller. |
| `snapshot` | no | string (at most 256 characters) | Read operations: the snapshot to read (id or latest). |
| `base_snapshot` | no | string (at most 256 characters) | `change.propose` and `edit.plan`: the snapshot the edits are written against. Must be an id, not `latest`. |
| `request_id` | no | string (at most 128 characters) | Caller-chosen idempotency key, scoped to workspace and caller. Bound to the request's input fingerprint. |
| `limits` | no | object (`limits`) | Request limits. Omitted fields take the defaults the capability manifest lists. Bytes are authoritative; tokens are never a request limit. |
| `params` | yes | object | Operation arguments; schemas/operations/&#60;operation&#62;.request.json. |

{/* END GENERATED envelope-fields */}

`request_id` is an idempotency key: the same `request_id` with the same input
returns the recorded result with `replayed: true`, and the same `request_id`
with different input is `conflict` (`request_id_reused`). Only edit and apply
operations record it; elsewhere it is echoed.

## Response envelope

Every response, success or error, has these fields, and exactly one of
`result` and `error`:

| Field | Meaning |
| --- | --- |
| `protocol`, `operation` | `operation` echoes the request. |
| `request_id` | Present when the request had one. |
| `workspace` | The workspace id, or `null` for `capabilities` and errors raised before a workspace was resolved. |
| `snapshot` | The snapshot the answer describes (for an edit, its base; for a candidate, the candidate's snapshot with `overlay` set), or `null`. See [Snapshots](#snapshots-and-workspaces). |
| `toolchain` | Compiler version and identity, edit rules identity, `language_profile` and `target`. |
| `coverage` | `completeness` (`complete`, `partial` or `unknown`), `exhaustive`, and `gaps`, each with a reason. An empty answer proves absence only when `exhaustive` is `true`. |
| `truncation` | `truncated`, the `limits` applied, bytes `used`, `omissions` (each with a reason, a count, up to 50 omitted node ids and expansion refs) and a `continuation` cursor or `null`. |
| `result` | The operation's result. |
| `error` | The [error object](#errors). |

A response never silently drops content. When a limit cuts an answer,
`truncation.truncated` is `true` and `omissions` say what was left out.
`max_bytes` counts the UTF-8 bytes of the compact JSON of `result`.

## Snapshots and workspaces

A **workspace** is one attached project root. `workspace.open` returns its
id; every later request except `capabilities` names it. The service serves
one root per process: the `--root` it was started with.

A **snapshot** is an immutable capture of the project's sources and inputs
(contracts and lock) under one compiler, language profile and target. Its id
is derived from its content. `latest` captures the files on disk now; the
response names the snapshot it used, so you can keep reading that exact
state. A snapshot's `semantic_state` says how far compilation got:

{/* BEGIN GENERATED semantic-states */}

- `syntax`: parsed only
- `resolved`: names resolved, not validated
- `validated`: compiled without errors
- `unavailable`: not even parsed

{/* END GENERATED semantic-states */}

In this build `unavailable` means there is no node graph, which is not always
a parse failure: a project whose source parses but that lacks its UI lock is
also reported as `unavailable` (with status `needs_preparation`). On an
`unavailable` snapshot, `node.find` answers `compile_failed`, `node.edits`
answers `compile_failed` (`not_validated`), and `project.overview` still
returns the diagnostics.

A read on a `syntax` or `resolved` snapshot is `partial` with a
`broken_source` gap. Edits need a `validated` base, except bounded repairs:
an edit on a broken base is accepted when it leaves fewer errors and none
outside the declarations it changed.

When a file changes on disk after a snapshot was captured, reads of that
snapshot still describe the captured state and add `snapshot.disk.state:
changed` with the changed paths. Read `latest` for the current files.

A **node id** names a node within one snapshot, for example
`element:Home/view/0/1`. Do not build or parse ids. To follow nodes to a
newer snapshot, use an edit's `id_map`, `changes.since` or `node.relocate`.
Every node carries a `version`, a fingerprint of its kind, name, file and
authored text; pass it as `expected_node_version` to refuse an edit if the
node changed.

A **candidate** is a proposed change: your operations applied to a private
copy of the base snapshot and compiled. It has an id and a version (1 when
created, increased each time you extend it) and is `open`, `applied` or
`discarded`. Only `change.apply` writes it to the project.

### node.find

Finds nodes by a case-insensitive substring of their name, id or a string
literal property value, with optional `kind`, `owner` and `path` filters.
Results are in document order, not ranked. More matches than `limit` are
reported as an omission: narrow the query.

{/* BEGIN GENERATED operation:node.find */}

**Params** ([`schemas/operations/node.find.request.json`](https://docs.axiomcore.dev/semantic-service/schemas/operations/node.find.request.json))

| Field | Required | Type | Meaning |
| --- | --- | --- | --- |
| `query` | yes | string (at most 200 characters) | Trimmed, case-insensitive substring of name, id, or a string-literal property value. Empty matches every node. |
| `kind` | no | string (at most 64 characters) | Exact kind filter; an unknown kind matches nothing. |
| `owner` | no | string (at most 1024 characters) | Only nodes owned (transitively) by this page or component. |
| `path` | no | string (at most 1024 characters) | Only nodes whose authored declaration is in this file. |
| `limit` | yes | integer (1..50) | Maximum number of nodes to return (1 to 50). More matches are reported as an omission; narrow the query. |

**Result** ([`schemas/operations/node.find.result.json`](https://docs.axiomcore.dev/semantic-service/schemas/operations/node.find.result.json))

| Field | Required | Type | Meaning |
| --- | --- | --- | --- |
| `nodes` | yes | array of object (`nodeSummary`) | Matching nodes, each with id, kind, name, file and version. |
| `matches` | no | array of object | One entry per node, same order: why it matched. |

**Error codes:** `invalid_arguments`, `not_found`, `internal`, `resource_limit`, `permission_denied`, `unsupported_operation`, `snapshot_expired`, `stale_snapshot`, `compile_failed`.

{/* END GENERATED operation:node.find */}

{"protocol": "axiom-agent-semantic/v1", "operation": "node.find", "workspace": "<workspace>",

## Errors

An error response has `error` instead of `result`. Decide what to do from
`code`, `reason`, `retryable` and `next_actions`; `message` is for people and
may change.

The one-shot command and `serve` answer a request that is not valid JSON, is
not a JSON object, or has no `protocol` field in the service's legacy format:
`error.code` is `invalid_request` (not a v1 code), and there is no
`operation`, `retryable` or `next_actions`. `serve` keeps reading the next
line. For a request without a `protocol` field, the message is
`protocol is missing; it must be "studio/v1"`.

Over MCP, `acore-semantic mcp` answers a message that is not valid JSON with
the JSON-RPC parse error `-32700`.

Ignore the `studio/v1` named in that message: send `axiom-agent-semantic/v1`.

| --- | --- | --- |
| `none` | The same request fails again. | Change the arguments, scope, limits or approach. Do not loop. |

### Error codes and what to do

| Code | Meaning | Default `retryable` | What a client should do |
| --- | --- | --- | --- |
| `stale_snapshot` | The base snapshot is not the current one, and a file the edit touches changed (reason `base_not_head`). | `after_refresh` | Call `changes.since` with your old snapshot and the ids you hold, map them, read the values again and propose on the current snapshot with a new `request_id`. |

## Apply, receipts and recovery

`change.apply` publishes a candidate to the local filesystem:

1. It checks the candidate version, that the required checks passed on that
   version, and that every file it writes still has the base content (a file
   the candidate creates must not exist). If not, it writes nothing:
   `precondition_failed` (`external_write`) for a file edited since, `conflict`
   (`concurrent_candidate`) for a file another candidate on the same base wrote.
2. It writes a journal and backups, then replaces the files one at a time
   (write, sync, rename). Each file is replaced atomically; the set of files is
   not atomic for other readers.
3. It returns a **receipt**: `receipt_id`, `request_id`, `input_fingerprint`,
   `outcome`, the candidate and its version, `base_snapshot`, `result_snapshot`
   (when applied), each file's SHA-256 before and after, the `id_map`, the
   journal entry and the time.

`outcome` is `applied`, `not_applied` or `unknown`. `unknown` means the
service could not tell whether writing finished, for example after an
interrupted rename; its journal stays `pending_reconcile`. The next
`change.apply` with the same `request_id` reconciles first: it returns the
recorded receipt if the files match the candidate, applies the candidate if
they match the base, and otherwise answers `conflict` (`recovery_required`)
without writing.

Inputs of the base that the candidate does not write are checked too: one
deleted or renamed since is `precondition_failed` (`external_write`), and one
edited since is accepted and listed in the result's `base_changes`.

### After an apply timeout

The time limit answers the client; it cannot undo or finish what the apply
was doing. A `change.apply` past `timeout_ms` is answered with:

- `code: resource_limit`, `reason: timeout`, `retryable: same_request`;
- `target`: the `candidate` and the `request_id`;
- `next_actions`: `change.apply` with the same params;
- `details`: `outcome`, `timeout_ms`, and `receipt` when one exists.

`details.outcome` is about this attempt:

- `not_applied`: this attempt stopped before it started writing and can no
  longer start. An earlier attempt with the same `request_id` may still have
  applied the change.
- `unknown`: this attempt had started writing, or reconciling an earlier
  attempt, and the service cannot tell how far it got. The files may already
  hold the candidate. `details.receipt` is the `unknown` receipt when the
  journal was written.

In both cases, send the same `change.apply` again with the same
`request_id`. The server process exits after a timed-out request, so start
it again first (for an MCP client, reconnect the server if its tools are gone). The answer is the recorded
receipt with `replayed: true`, or the interrupted apply is reconciled from its
journal and the candidate is applied once. A resend with the same
`request_id` is never `request_id_reused` and never applies twice. Do not
propose again, use a new `request_id`, or edit the files by hand to retry an
apply: after the change was applied, a new `request_id` for the same candidate
is `precondition_failed` (`candidate_applied`).

### Guarantees and their limits

Publication is proven against process kills at every step: after a kill the
apply ends applied, rolled back, or reported as needing attention, with no
half-written file. It is not proven against power loss or operating system
crashes, and there is no remote publication. The full list of guarantees is in
the [Support matrix](/semantic-service/support-matrix#publication).

## Compatibility

The manifest's `protocol.status` is `frozen`, and `protocol.frozen_operations`
lists the operations frozen in v1: `capabilities`, `workspace.open`,
`project.overview`, `node.find`, `node.get`, `node.edits`, `graph.query`,
`context.build`, `impact.analyze`, `changes.since` and `node.relocate`. Read
that list from `capabilities` rather than from this page. Error `code` is a
closed list; `reason` is an open string that can gain values. A client sends
an optional field only when `capabilities` lists the operation as
implemented. A planned operation or edit kind answers `unsupported_operation`
(`not_implemented`).
